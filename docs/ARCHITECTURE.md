# Architecture

## Source layout

| Path | Responsibility |
|---|---|
| `Sources/WardCore` | Vault lifecycle, cryptography, data models, TOTP, search, imports, audits, SSH, and browser protocols; no UI. |
| `Sources/Ward` | AppKit windows, SwiftUI views, and application controllers. |
| `Sources/WardBrowserHost` | Chrome native messaging helper. |
| `Sources/WardCLI` | Command-line executable and MCP server. |
| `BrowserExtension` | Chrome Manifest V3 extension. |
| `Tests` | Core, app, and browser extension tests. |
| `tools` | Build support, generators, and integration checks. |

## Vault lifecycle and storage

`VaultSession` owns the vault lifecycle over `VaultStorage`. Tests replace storage with an in-memory implementation that can simulate failures. The app's `VaultStore` publishes session state and moves key derivation off the main thread.

The vault occupies one login Keychain item with service `local.ward` and account `vault`. Its `VaultEnvelope` contains an AES-256-GCM vault key wrapped by a key derived from the master password using PBKDF2-SHA256 with 600,000 iterations. Changing the master password also rotates the vault key through `rekey`.

After changes, Ward writes an encrypted backup to `~/Library/Application Support/Ward/Backups`. A backup failure does not undo an already saved vault change; it is reported through `VaultSession.backupError`.

`SingleInstance` uses `flock` to enforce one app instance per user. `VaultSession` rejects writes over an external Keychain change with `changedElsewhere`.

Security settings such as automatic locking, clipboard lifetime, agent policy, backup count, and mirror location live in `Vault.security`. Values needed before unlock, including the failed-password counter and the agent-enabled flag, live in the same Keychain item's `VaultEnvelope` rather than UserDefaults.

## Companies, projects, and services

Work entries are organized by `Company`. Projects and services have a `companyID`, and child projects belong to their parent's company. Projects form a tree through `Project.parentID`, with arbitrary depth.

An entry's `serviceID` identifies a provider, SaaS product, or external API account. Combined with `projectID`, it is a project's account in that service. Without a project, it is a shared account visible to the projects in `projectIDs`. An entry with neither a project nor a service is a company-wide credential identified by `Entry.companyID`.

`Projects.swift` handles relationships and protects against cycles and dangling references in damaged backups. `assignOrphansToCompany` assigns work data without a company during unlock and import. Legacy `integrations` and `integrationID` keys remain readable after integrations were renamed to services.

`Entry.environments` supports several environments per entry. `environment` exposes the first environment, and the old serialized field remains readable. A VPN used in Stage and Production appears in both project columns.

## Entry details and drafts

`Entry.preSteps` contains `PreStep` values: text or a reference to a connection entry such as a VPN or tunnel (`Entry.isConnection`). Legacy steps are stored as strings. Permanently deleting a connection through `purge` removes references to it.

SSH material and certificates live in `Entry.ssh` and `Entry.certificate`; parsing is implemented in `KeyMaterial.swift`. `EntryAddress` represents an entry's address. `sshKeyEntryID` and `certificateEntryID` link to another entry's material. Resolution, including `Vault.sshKey(for:)`, supports no chains. Custom values live in `Entry.fields`; hidden fields are excluded from search and copied with password handling.

Encrypted editor drafts live in `Vault.drafts` as `EntryDraft` values. They are persisted one second after editing, on lock, and on quit. Saving, discarding, or permanently deleting an entry removes its draft. Drafts are excluded from search, audits, exports, and backup merges.

## SSH agent and certificates

`SSHAgent.swift` implements the agent protocol and socket. `SSHSigning.swift` handles keys and signing, including RSA through `SecKey` and CRT parameters computed with `BigUInt`. `Blowfish.swift` implements OpenSSH passphrase handling with `bcrypt_pbkdf`; its generated tables use digits of π.

`AgentController` presents approval requests and unlocks the app when needed. Debug builds provide an agent demo mode described in [development](DEVELOPMENT.md).

Nebula certificates are not X.509. `Nebula.swift` reads v1 protobuf and v2 DER certificates. V2 fingerprints match Nebula's `certificateV2.Fingerprint()`. Optional tests compare results against `nebula-cert`.

## Autofill and browser integration

Autofill validates the site using the embedded Public Suffix List and the URL scheme, including HTTPS requirements. `PublicSuffix.swift` implements matching. `PublicSuffixList.swift` is generated by `swift tools/update-psl.swift`. Clipboard autofill uses `PasteOffer` to wait until the target app consumes one string before offering the next.

Chrome requests follow this path:

```text
BrowserExtension → ward-browser-host → browser.sock → BrowserController
```

The Manifest V3 extension has a stable ID derived from the public `key` in its manifest. The native messaging helper is bundled in `Contents/Helpers` and has its own signing identifier. Ward verifies the helper's audit token and matching signing team, and `BrowserPeerCheck` verifies that a Google-signed process launched it. The normal bridge is disabled without a Team ID.

`BrowserBridge.swift` and `Passkeys.swift` implement request handling, WebAuthn, CBOR, and Public Suffix List-based rpId validation. See [extension permissions](CHROMEWEBSTORE.md) for page-script boundaries and request limits.

## UI conventions and privacy

The UI uses `Theme` and `Format` for colors and formatting. `wardField` provides field highlighting; `hoverBackground` and `hoverLink` provide pointer feedback. Windows and sheets disable the system blue focus ring with `.focusEffectDisabled()`.

Hide Data mode uses `Prefs.hideData`, toggled with ⌘⇧H. Windows apply `.redacted(reason: .privacy)` and sensitive fields use `.privacySensitive()`.

The password breach check uses HIBP k-anonymity and runs only after an explicit action and confirmation. Key tests generate material with system `ssh-keygen` and `openssl` at runtime; production keys do not belong in the repository.
